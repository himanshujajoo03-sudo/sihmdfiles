# MLSpec — AI / ML Specification
### SIH26069 — National Weather Big Data Analytics Platform
### See `PRD.md` for document index, `TechSpec.md` §2/§8 for how these models are served (decoupled model-serving services, never embedded directly in the stream-processing job), `Schema.md` for the exact fields each model reads/writes.

**Tagging:** [PHASE 1] = simplest defensible model for this signal, buildable with little or no labeled data, ships first. [PHASE 2+]/[PHASE 3+] = the fuller target model, gated specifically on real data volume becoming available — never gated on "when we feel like it." Every upgrade in this file replaces its predecessor behind a stable interface (same inputs/outputs), per the graceful-degradation principle in `TechSpec.md` §1.

**Non-negotiable rule carried through every section below:** never train any model in this file on synthetic or guessed labels to "have something working." An unrealistically perfect evaluation result (near-100% across the board) is a signal to investigate the data, not a result to report proudly — see `Guardrails.md`.

## 1. Text Classification & Entity Extraction

### [PHASE 1] Lightweight classifier + rule-based fallback
- A fast, low-resource text classifier (e.g., TF-IDF features + a simple linear classifier such as Logistic Regression) trained on whatever real labeled report text exists at launch, however small.
- A rule-based keyword/phrase classifier as an always-available fallback when the trained model is unavailable or its confidence is low — must include basic multilingual keyword coverage (Hindi/Marathi terms and their negations, e.g. "not," "नहीं," "नाही") from day one, not as an afterthought.
- **Interface contract (must not change when upgraded to Phase 2+):** input = report text (+ optional structured hints); output = `classified_category` (from the taxonomy, `Schema.md` §1.1) + `classification_confidence` (0–1).

### [PHASE 2+] Fine-tuned multilingual transformer (XLM-RoBERTa or MuRIL) + NER
- **Why this upgrade matters:** genuinely understands Hindi/Marathi/Hinglish/English in context, rather than pattern-matching keywords — directly serves the multilingual-reach goal in `PRD.md` §3.
- **NER addition:** extracts location mentions, dates, and severity language directly from unstructured text — most valuable for sources (social media, news) where clean structured metadata (city/state/GPS fields) isn't reliably present, unlike a structured citizen-report submission form which already collects these fields directly.
- **Gate condition:** do not begin fine-tuning until real labeled text volume is sufficient (see §7 data requirements table) — until then, Phase 1's lightweight classifier remains primary, not a placeholder to be embarrassed about.
- Runs as its own model-serving service (`TechSpec.md` §9 — `classification-service`), called by the stream-processing job, never imported directly into it.

## 2. Duplicate / Near-Duplicate Detection

### [PHASE 1] Lexical similarity
- Token-overlap similarity (e.g., Jaccard) between report texts, combined with source/category/time/location signals into a single weighted duplicate score:
```
D = (Σ w_k · s_k) / (Σ w_k for available signals)
```
where `s_k` ranges over: text similarity, exact source-ID match, source-URL match, category compatibility, time-bucket proximity, geographic distance — weighted and renormalized across whichever signals are actually available for a given pair (a missing signal's weight redistributes across the rest, the score never breaks).
- Thresholds: a "probable duplicate" score merges two reports into one event; a "possible duplicate" score flags for analyst attention rather than auto-merging.

### [PHASE 2+] Semantic similarity via embeddings
- Add a semantic signal generated by a multilingual sentence-embedding model (e.g., a multilingual E5-family model), stored via `pgvector` (`Schema.md` §4), compared via cosine similarity:
```
S_semantic = cos(e_i, e_j) = (e_i · e_j) / (‖e_i‖ ‖e_j‖)
```
- **Why this matters:** catches duplicates worded completely differently ("water entered homes" vs. "flooding reported in residential area") that pure lexical matching misses — especially important across languages/dialects.
- **Prefix convention (model-specific, verify against whichever embedding model is chosen):** many multilingual embedding models expect different prefixes for "stored/indexed document" text vs. "live query" text — get this right per the specific model's documentation, since using the wrong prefix silently degrades match quality without throwing an error.
- Runs as its own model-serving service (`embedding-service`, `TechSpec.md` §9) — if unavailable, duplicate detection automatically falls back to Phase 1's lexical-only scoring, never breaks.

## 3. Credibility / Evidence Fusion

### [PHASE 1] Hand-designed weighted formula
```
C = w1·T_source + w2·R_corrob + w3·A_weather + w4·K_temporal + w5·K_spatial + w6·Q_content
```
Suggested starting weights (tune based on real early usage, document any change and why):
```
w1 = 0.30 (source trust)       w4 = 0.10 (temporal consistency)
w2 = 0.25 (corroboration)      w5 = 0.10 (spatial consistency)
w3 = 0.20 (weather agreement)  w6 = 0.05 (content quality)
```
- `R_corrob` (corroboration) must count **distinct contributing source types** (`Schema.md` §2.2 `contributing_source_types`), not raw report count — otherwise a coordinated set of reposts from one source type can artificially inflate trust.
- **Non-negotiable implementation rule:** the human-readable reasons behind this score (`credibility_reasons`, `Schema.md`) must be generated and stored every time this formula runs, on every code path that can produce a score — never a hardcoded placeholder score with empty reasons. This directly serves the explainability requirement in `PRD.md` §7 and the UI contract in `Design.md` §4 (`CredibilityPanel`).
- Weights here are explicitly hand-designed, not learned — state this honestly if asked; this is a legitimate, explainable design choice for Phase 1, not a stopgap to be ashamed of.

### [PHASE 3+] Learned fusion model (XGBoost)
- Once real labeled outcome data exists — specifically, accumulated analyst verification decisions from the Admin module (`AppFlow.md` §3) — train a gradient-boosted model to learn which combination of input signals actually predicts a genuinely verified event, rather than relying on hand-set weights.
- **Candidate input features:** everything the Phase 1 formula uses, PLUS the additional signals introduced elsewhere in this file once they exist: structured-data anomaly score (§4), satellite-derived signal (§5), time-series/forecast risk signal (§6), semantic duplicate/corroboration score (§2).
- **Hard gate — do not shortcut this:** this model requires real ground-truth outcomes (an analyst's actual verify/reject decision), which by definition cannot exist before the platform has been live and used for some real operational time. Do not synthesize or guess these labels to start earlier — this exact mistake (training on invented/templated labels) produces a model that looks good on paper and means nothing in practice.
- **Must retain explainability** when this replaces the Phase 1 formula — use a feature-attribution method (e.g., SHAP or equivalent) so `credibility_reasons` remains a genuine, specific explanation, not a generic "the model said so."
- The Phase 1 hand-weighted formula remains the fallback if this model is ever unavailable — never fully retired, only demoted to fallback tier.

## 4. Structured Weather Data (rainfall, wind, temperature, pressure)

### [PHASE 1–2] Isolation Forest for anomaly detection
- Unsupervised — needs only a baseline of real historical value ranges per region/season, no labels required. Build this early; it's genuinely low-effort relative to its value.
- Answers: "is this specific structured reading unusual compared to normal patterns for this location and season?"
- Output feeds as one input signal into the credibility/fusion layer (§3) — an anomalous reading strengthens or weakens the weather-agreement factor, it does not independently declare an event true or false.

### [PHASE 2+] Gradient boosting (XGBoost/LightGBM) for structured risk scoring
- Distinct from Isolation Forest: this is a supervised risk-scoring task, needs labeled outcomes tied to structured readings (define what "outcome" means for this specific signal before starting — e.g., did this anomalous reading correspond to a later-verified event).
- Chosen over deep learning for this data type specifically because gradient boosting is the standard, well-performing, fast, and explainable choice for tabular/numeric features — no need for a heavier architecture here.

## 5. Satellite / Aerial Imagery

### [PHASE 3+] Swin Transformer (primary chosen architecture)
- Hierarchical, shifted-window attention handles the multi-scale spatial patterns in satellite imagery (cloud systems and storm formations spanning very different physical sizes) more effectively than a fixed-receptive-field CNN, while remaining more compute-efficient than a plain Vision Transformer at typical satellite tile resolutions.
- **Data source:** MOSDAC (ISRO) — cloud imagery, cyclone bulletins, atmospheric data. Registration/access process should be started early, independent of when the model itself gets built, since approval timelines are outside the team's control.
- **What it detects:** cloud-system/storm-pattern classification, flood-extent estimation from imagery.
- **Alternative/ensemble candidates:** CNN-based models purpose-built for remote sensing (fine-tuned ResNet/EfficientNet, or specialized flood-detection model families from research groups working on disaster mapping) — evaluate as a fallback or ensemble partner if Swin's real-world performance on actual MOSDAC imagery underperforms expectations. **Never use a generic ImageNet-pretrained CNN as-is** — satellite imagery's visual patterns (spectral bands, top-down perspective, scale) are too different from normal photographs for that to transfer well.
- Output feeds into §3's fusion layer as an additional structured signal — never a gating dependency the core pipeline requires to function.

## 6. Time-Series Patterns (storm trajectory, rainfall trend)

### [PHASE 3+] LSTM baseline → Transformer-based time-series models
- The one model type in this file that's forward-looking (prediction) rather than purely classificatory — models sequences over time (is rainfall trending up over the last N hours, where is a storm system likely heading).
- Start with an LSTM as the simpler, lower-data/compute baseline; evaluate a Transformer-based time-series architecture as a second iteration once real historical time-series depth and volume justify the added complexity.
- **Data source:** the historical/reference batch data path (`TechSpec.md` §3) — this is exactly the kind of longitudinal data this model type needs, and it's already part of the planned architecture regardless of this specific model.
- **Product distinction:** this model's output is a genuinely new capability (a forward-looking prediction), not a replacement for any existing scoring — it can additionally feed into §3's fusion layer as a forward-looking risk signal for events in a storm's predicted path, but its primary value is a standalone predictive-alerting feature.

## 7. Priority / Triage Scoring

### [PHASE 1] Two-tier design
1. **Pre-ingestion gate (cheap, <5ms):** a lightweight keyword/severity-threshold check run before the report even enters the message queue — decides only "does this go through the fast lane or the normal lane" (`TechSpec.md` §4.3). Deliberately NOT the full formula below; must be cheap enough to run inline at ingestion time.
2. **Queue-ordering formula (used once in the Admin module's Verification Queue, `AppFlow.md` §3):**
```
P = w1·S_v + w2·U + w3·C + w4·R_corrob + w5·L_risk + w6·min(cap, t_wait / decay)
```
where `S_v` = severity value, `U` = urgency signal, `C` = credibility score (§3), `R_corrob` = corroboration, `L_risk` = location risk, and the final aging term ensures a lower-priority item waiting a long time gradually rises in the queue — preventing indefinite starvation of anything not flagged urgent at intake. Suggested starting weights, tune with real usage: `w1=0.40, w2=0.20, w3=0.15, w4=0.10, w5=0.10, w6=0.05`.

## 8. Model Serving & Integration

- Every model in this file (Phase 1 and beyond) runs as its own model-serving service, per `TechSpec.md` §2/§8 — called over a lightweight internal API by the stream-processing job, never imported directly as a library into it. This is the specific design decision that prevents cross-service dependency/version conflicts as a whole category of problem, and it means upgrading any single model (e.g., swapping the Phase 1 classifier for the Phase 2+ fine-tuned transformer) never requires touching the stream-processing job's own code or dependencies.
- Every model-serving service must expose a health/readiness check the stream-processing job can use to decide whether to call it or fall back — graceful degradation must be an explicit, checkable state, not an assumption.

## 9. Data Requirements Summary (check before starting ANY [PHASE 2+]/[PHASE 3+] model)

| Model | Minimum real data needed | Notes |
|---|---|---|
| Isolation Forest | Historical value-range baselines (no labels) | Can start almost immediately |
| Fine-tuned XLM-R/MuRIL | Thousands of real, diverse, labeled multilingual text examples per category | Volume/language-balance must be verified before starting, not assumed |
| Semantic embeddings (duplicate detection) | A pretrained multilingual embedding model is usable off-the-shelf; no custom training required to START, though evaluating it against real report pairs before trusting it in production is still required | Lower-barrier than the other Phase 2+ items |
| XGBoost/LightGBM (structured risk) | Real structured readings with a defined, real notion of outcome | Define "outcome" concretely before starting |
| Swin Transformer (satellite) | Labeled MOSDAC imagery (or a bootstrap public remote-sensing dataset) | Gated on MOSDAC access completing first |
| LSTM/Transformer (time-series) | Sufficient real historical time-series depth and continuity | Verify actual depth, don't assume the historical batch path already has enough |
| XGBoost fusion layer | Real accumulated analyst verification decisions | Longest lead time — requires the platform to be live and in real use first |

---

## 10. Explicit Non-Goals

- No model in this file is scaffolded as active, callable production code before its data requirement (§9) is genuinely met. A stub that always returns a placeholder value is worse than no function at all — it can silently masquerade as a working signal downstream.
- No Phase 1 fallback (lightweight classifier, rule-based classifier, hand-weighted credibility formula, lexical duplicate detection) is ever fully removed when its Phase 2+/3+ upgrade ships — every upgrade is additive-with-fallback, never rip-and-replace.
